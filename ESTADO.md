## El cambio de stack (12 de septiembre)

El proyecto pasó de **PHP 8 puro + MySQL + Flutter** a **NestJS + React +
React Native + PostgreSQL + Azure**. Se tiraron 1.749 líneas de PHP y se
conservó todo lo demás: el modelo de datos, el contrato REST, el diseño de
seguridad, las plantillas de reporte y el documento.

> ⚠️ **Pendiente con el docente.** El enunciado, tal como está registrado,
> prohíbe frameworks (menciona React por nombre) y exige Flutter para el móvil.
> El stack nuevo contradice las dos cosas, y el capítulo 5 del documento declara
> el stack. **Es lo más urgente de confirmar.**

### Cómo se migró la base

`scripts/mysql-a-postgres.mjs` convierte el esquema de forma reproducible:

| Transformación | Cuántas |
|---|---|
| `AUTO_INCREMENT` → `GENERATED BY DEFAULT AS IDENTITY` | 52 |
| `ENUM(...)` → `CREATE TYPE ... AS ENUM` | 39 |
| `TINYINT(1)` → `BOOLEAN` | 37 |
| `DATETIME` / `TIMESTAMP` → `TIMESTAMPTZ` | 48 |
| `ON UPDATE CURRENT_TIMESTAMP` → trigger | 8 |
| `FULLTEXT KEY` → índice GIN con `to_tsvector('spanish', ...)` | 1 |
| Claves ajenas movidas a `ALTER TABLE` al final | 91 |

Las 8 plantillas de reporte se reescribieron a mano
(`scripts/plantillas-reporte-postgres.mjs`) y se validaron con `EXPLAIN`.

### Decisiones que sostienen el sistema

- **La variante es la unidad vendible** (producto × talla × color). El stock, el
  SKU y los precios cuelgan de ella.
- **`StockService` es la única puerta al inventario.** Bloquea la fila con
  `SELECT ... FOR UPDATE` antes de leerla (dos cajas vendiendo la última unidad
  a la vez es un caso real) y escribe siempre el movimiento junto al cambio de
  stock, así el kardex no se puede desincronizar.
- **El stock se reserva al confirmar y sale al preparar.** Eso evita vender lo
  que ya no está y que un pedido impago trabe el inventario. La venta de
  mostrador inmediata es la excepción: descuenta en el acto.
- **El precio lo decide el servidor**, siempre. Del cliente solo puede venir un
  código de cupón, nunca un monto.
- **Se aplica una sola promoción**, la mejor para el cliente. Acumularlas es
  como se terminan regalando productos.
- **Los correlativos salen de secuencias de PostgreSQL.** Un `MAX(numero)+1` le
  daría el mismo número a dos operaciones simultáneas.
- **La clave de idempotencia** hace que una venta registrada sin conexión se
  reintente sin cobrarse ni descontarse dos veces.
- **Los permisos viven en la base.** Un administrador crea un rol, le asigna
  permisos y el cambio rige en la petición siguiente. Hay una prueba que lo
  recorre entero.

Las pruebas encontraron tres defectos reales que ya están corregidos:

1. Varios POST devolvían `201` sin crear ningún recurso.
2. `cancelar` comprobaba el estado antes que el permiso, así que a un tercero le
   contestaba "no se puede cancelar un pedido entregado" — y ese mensaje le
   confirmaba que el pedido existía. Ahora autoriza primero y devuelve 404.
3. El detalle del pedido no exponía el id de cada línea, con lo que un cliente
   no podía armar una solicitud de devolución.

### Seguridad

- `npm audit`: **0 vulnerabilidades**. Hubo que forzar `multer` a 2.3.0 —
  `@nestjs/platform-express` arrastra la 2.2.0, con cuatro avisos de denegación
  de servicio, y es la que recibirá las imágenes de producto.
- El JWT se verifica con `algorithms: ['HS256']`, lo que bloquea el ataque de
  `alg=none` (hay una prueba que lo construye y lo manda).
- Del refresh se guarda solo el SHA-256, y es rotatorio.
- Desactivar a alguien o cambiarle la contraseña revoca sus sesiones abiertas.
- `trust proxy` está puesto para que detrás del proxy de Azure el limitador vea
  la IP real y no la del balanceador.

## Cómo levantar todo

```bash
docker start aurora-db          # o el docker run de la primera vez (README)
npm install
npm run db:cargar               # ⚠ borra todos los datos
npm run build
npm run api
npm run pruebas
```

> **No usar `prisma db push` ni `prisma migrate`.** La fuente de verdad es
> `database/schema.postgres.sql`; Prisma borraría los CHECK, el índice GIN de
> búsqueda y las dos vistas.
